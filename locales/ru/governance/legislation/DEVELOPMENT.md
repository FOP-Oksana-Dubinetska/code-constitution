# Регламент разработки репозитория «Конституция кода»

## Проект производного акта

Идентификатор акта: `kcr-act-development-001`.

Редакция: `0.3.0-draft`.

Классы Законодательства: Z01, Z02, Z07, Z08, Z09, Z11.

Конституционное основание: часть I, § 7; I.1–I.3, II.4, V.4–V.5, VI.1,
VI.4, P04, P06, P16 и P17 проекта Учредительного профиля.

Акт устанавливает порядок изменения корпуса и будущих программ его обработки.
Его переносимое ядро пригодно для других TypeScript-репозиториев. Локальное
расширение регулирует устойчивые ID, Markdown-источник, дробление, обратную
сборку и удостоверение «Конституции кода».

## 1. Классы правил

Каждое правило относится к одному из двух классов:

- `BASE` — переносимое правило разработки, форматирования, линтинга,
  типизации, тестирования и зависимостей;
- `KCR` — локальное правило корпуса «Конституции кода», его источников,
  идентификаторов, манифестов и сборки.

Другой репозиторий вправе принять `BASE` как исходный профиль и определить
собственное локальное расширение. Копия указывает исходную редакцию, принятые
отклонения и собственное пространство идентификаторов.

## 2. Архитектура источников и выпусков

### BASE-S01. Каноническое состояние

Один Git-коммит образует каноническое состояние проекта. Каждый файл в этом
состоянии имеет один из статусов:

- `source` — редактируемый источник;
- `generated` — воспроизводимое производное представление;
- `fixture` — намеренно зафиксированный пример или ожидаемый результат;
- `external` — полученный извне материал с указанным происхождением;
- `report` — доказательство проверки либо выпуска.

Статус определяется путём и манифестом. Изменение статуса проходит
нормотворческую процедуру.

### KCR-S01. Материнский документ

`/locales/ru/CONSTITUTION_CODE.md` является каноническим материнским
документом универсального корпуса первой редакции. Он содержит нормативные
части, форму Учредительного профиля, карту Законодательства и явные границы
исследовательского комментария.

Файлы профиля и Законодательства самого репозитория являются самостоятельными
каноническими источниками. Их совокупность с материнским документом образует
одно каноническое состояние на уровне коммита.

### KCR-S02. Производные части

Дробление создаёт производные представления Конституции, формы профиля,
Законодательства и исследовательского корпуса. Каждый результат содержит либо
сопровождается:

- идентификатором источника и его хешем;
- версией правил дробления;
- перечнем включённых устойчивых ID;
- порядком следования фрагментов;
- собственным статусом;
- ссылкой на результат проверки, когда такой результат существует.

Ручная работа в производных частях допускается в объявленном рабочем режиме.
Её результат входит в канонический источник только через обратную сборку,
сравнение, полную проверку и обычное принятие изменения.

### KCR-S03. Локали и README

Реестр локалей учреждает `ru`, `uk` и `en`. Каждая локаль получает
машиночитаемый манифест с кодом BCP 47, статусом, исходной редакцией, авторами
или переводчиками, проверяющими и датой последней содержательной сверки.
Статус `planned` сообщает только о принятом направлении работы. Полным
нормативным источником первой редакции является `ru`; `uk` и `en` получают
информационный статус после публикации полного перевода и успешной проверки
структурного соответствия.

Корневой README разворачивает английское описание. Полные украинская и русская
версии помещаются в сворачиваемые секции. Языковая форма README не изменяет
нормативный язык корпуса.

Копия, изменившая текст Конституции, обязана заменить проектный блок README:
собственное наименование, официальный репозиторий, держателей полномочий и
заявление об официальном статусе. Она указывает исходную редакцию, сохраняет
обязательную атрибуцию и явно описывает изменение. Сохранение исходного
проектного блока после содержательного изменения считается ложным
утверждением идентичности.

### KCR-S04. Связанная научная публикация

Репозиторий не архивируется в Zenodo и не получает DOI. Статья,
исследовательские заметки и иные перечисленные материалы публикуются отдельной
записью, авторами которой являются Sam Starling и Oksana Dubinetska. Её DOI
записывается как идентификатор связанной работы. Метаданные, значки и
цитирование не представляют этот DOI как идентификатор репозитория,
программного выпуска либо нормативного корпуса.

## 3. Технологический профиль

### BASE-T01. Среда и язык

Программы репозитория пишутся преимущественно на TypeScript и выполняются в
Node.js 24 LTS. JavaScript допускается в конфигурации, интеграционной границе
либо ином месте, где его использование прямо обусловлено инструментом; он
подчиняется применимым правилам модульности, именования, обработки ошибок и
линтинга. CSS образует необязательный декларативный профиль и проверяется
только при наличии CSS-источников.

Точный patch-релиз Node.js и точные версии зависимостей фиксируются манифестом
инструментов, `package.json` и `package-lock.json`. Менеджером пакетов является
npm; его точная версия также входит в манифест. CI использует ту же
поддерживаемую линию и устанавливает зависимости командой `npm ci`. Другой
lockfile в каноническое состояние не входит.

Исходный код использует ECMAScript modules. `tsconfig` включает строгую
проверку и как минимум параметры:

- `strict`;
- `noUncheckedIndexedAccess`;
- `exactOptionalPropertyTypes`;
- `noImplicitOverride`;
- `useUnknownInCatchVariables`;
- `noFallthroughCasesInSwitch`;
- `forceConsistentCasingInFileNames`.

Сценарии `npm run format`, `npm run lint`, `npm run typecheck`, `npm test` и
`npm run check` образуют стабильный локальный интерфейс инструментов. Замена
внутренней программы сохраняет семантику сценария либо проходит изменение
настоящего акта.

### KCR-T01. Представления данных

Структурные операции над Markdown используют синтаксическое дерево
`unified`/`remark` с поддержкой GFM. Регулярные выражения применяются для
локальных лексических проверок и не определяют структуру заголовков, таблиц,
списков или вложенных блоков.

Учредительный профиль и другие редактируемые проектные данные используют YAML
либо JSON согласно утверждённой схеме. Их структура проверяется JSON Schema
Draft 2020-12. Манифесты сборки и происхождения используют JSON с
детерминированным порядком ключей при сериализации.

### BASE-T02. Граница внешних данных

Файл, аргумент командной строки, переменная среды, ответ API и содержимое Git
считаются внешним вводом. Адаптер чтения преобразует ввод в `unknown`,
проверяет схему и только затем создаёт внутреннюю типизированную модель.
Утверждение типа без проверки внешнего значения запрещено.

Файловая система, Git, консоль и сетевые сервисы доступны ядру через явные
адаптеры. Часы и хеширование представлены отдельными портами: время описывает
момент наблюдения, а хеш — точное содержимое. Их совместное использование в
отчёте не превращает их в одну зависимость. Чистая логика классификации,
сопоставления ID и построения плана сборки не обращается к глобальному
состоянию.

## 4. Порядок изменения

### BASE-C01. Единица изменения

Изменение имеет одну распознаваемую цель. Его описание сообщает намерение,
затронутые области, способ проверки и последствия. Исправление дефекта
содержит тест, воспроизводящий прежнее поведение, когда такой тест технически
возможен.

### KCR-C01. Классификация изменения

Изменение получает один из классов:

- `editorial` — орфография, пунктуация, ссылка или форма без изменения тезиса;
- `normative` — изменение содержания положения либо проектного правила;
- `structural` — перемещение, разделение, слияние или изменение состава
  производных частей;
- `tooling` — изменение программы, схемы, конфигурации или CI;
- `release` — подготовка удостоверенного выпуска;
- `emergency` — временная мера по P14.

Классы могут сочетаться. Наивысший затронутый уровень определяет процедуру.

### BASE-C02. Проход изменения

Обычный проход включает:

1. запись намерения;
2. изменение в отдельной ветви;
3. локальную автоматическую проверку;
4. рассмотрение различий;
5. обязательные проверки CI;
6. явное согласие компетентного носителя;
7. объединение без обхода защищённых проверок;
8. регистрацию результата и, при необходимости, выпуск.

Автоматическая успешная проверка подтверждает соблюдение выраженных правил.
Человеческое согласие подтверждает принятие содержания и последствий.

### KCR-C02. Изменение положения

Редакционная правка сохраняет устойчивый ID тезиса. Разделение, слияние,
замена и выведение положения создают записи происхождения. Новый тезис
получает следующий свободный ID в соответствующем пространстве. Выведенный ID
сохраняется и повторно не выдаётся.

Нормативное изменение обновляет связанный вопрос либо содержит мотивированное
объяснение сохранения прежней формулировки вопроса. Изменение состава частей
обновляет манифест распределения.

## 5. Форматирование файлов

### BASE-F01. Общие свойства

Текстовые файлы используют UTF-8, перевод строки LF и завершающий перевод
строки. Пробелы и знаки табуляции в конце строки запрещены. Исходный код
использует табуляцию для уровня отступа с отображаемой шириной `2`. Формат,
грамматика которого требует пробелов, включая Markdown и YAML, следует
собственному явному правилу.

Имена файлов программного кода используют `kebab-case`; имена
TypeScript-файлов тестов завершаются `.test.ts`. Остальные правила имён
установлены BASE-N01–BASE-N03 и BASE-CSS-N01.

### BASE-F02. Prettier

Prettier форматирует TypeScript, JavaScript, CSS, JSON, YAML и поддерживаемые
конфигурационные файлы со следующими значениями:

| Параметр | Значение |
| --- | --- |
| `printWidth` | `100` |
| `tabWidth` | `2` |
| `useTabs` | `true` |
| `semi` | `true` |
| `singleQuote` | `true` |
| `trailingComma` | `all` |
| `arrowParens` | `always` |
| `bracketSpacing` | `true` |
| `endOfLine` | `lf` |

`printWidth` задаёт целевую ширину автоматического переноса. Он не образует
абсолютный запрет для неделимого URL, хеша, пути или другого атомарного
значения. Решение форматтера является каноническим для поддерживаемой
синтаксической формы и не определяет смысловую группировку операций.

### BASE-F03. Строфическая организация

Строфа кода по G031 представляет собой непрерывную группу соседних выражений,
обслуживающих одно локальное поднамерение. Пустая строка отделяет разные фазы
операции, например получение данных, проверку, преобразование, внешний эффект
и формирование результата. Этот перечень описывает возможные функции строфы
и не требует одинаковой последовательности от каждой функции.

Соседние выражения одной семантической роли сохраняют параллельную
синтаксическую форму и порядок аргументов. `return`, выброс ошибки и передача
эффекта завершают соответствующую смысловую фазу. Пустая строка не разделяет
одно неделимое выражение и не создаёт декоративную строфу без смены
поднамерения.

Комментарии сообщают основание решения, условие контракта, существенный риск
или причину исключения. Комментарий, только повторяющий действие читаемого
выражения, смысловой строфы не образует.

### BASE-F04. Граница автоматизации стиля

Prettier управляет локальной синтаксической формой. ESLint и собственные
проверки контролируют только объективно распознаваемые границы и параллельные
конструкции. Смысловое единство строфы, достаточность имени и уместность
комментария подтверждаются человеческим ревью.

Однострочная функция, декларативная таблица, конфигурация, внешний либо
производный файл вправе иметь иную естественную форму. Исключение из
автоматической проверки оформляется по BASE-X01; общая особенность класса
файлов закрепляется локальным правилом по BASE-X02.

### KCR-F01. Markdown

Prettier не форматирует канонический нормативный и исследовательский Markdown.
Автоматические проверки сохраняют авторские переносы внутри смыслового абзаца,
а пустая строка отделяет его от соседнего блока. Заголовки используют
ATX-форму. Вложенные элементы списка получают отступ в два пробела. Кодовые
блоки всегда называют язык, когда содержимое относится к определённому
синтаксису.

Markdown проверяется `markdownlint-cli2`. Правило длины строки `MD013`
отключено для корпуса, поскольку механический перенос прозы ухудшает
адресуемость блока и создаёт шум различий. Правила запрета табуляции,
завершающих пробелов, пропуска пустых строк вокруг заголовков, неправильной
иерархии заголовков и неоднозначных списков остаются обязательными.

Таблица способна содержать строку длиннее целевой ширины. Её структура и число
ячеек проверяются отдельно.

## 6. Линтинг программного кода

### BASE-L01. Конфигурация

ESLint использует flat config. TypeScript проверяется наборами
`strictTypeChecked` и `stylisticTypeChecked`; первый включает рекомендуемые и
строгие типизированные правила. JavaScript проверяется всеми применимыми
правилами того же профиля. Конфигурация совместимости с Prettier загружается
последней и устраняет пересечение форматирующих правил.

Линтинг с информацией о типах использует project service. Предупреждения CI
запрещены: каждое срабатывание имеет статус ошибки либо правило явно
отключено с нормативным основанием.

### BASE-L02. Обязательные ограничения

Проект применяет следующие правила содержания:

- неиспользуемая переменная или импорт запрещены;
- необработанный Promise запрещён;
- небезопасные операции с `any` запрещены;
- явный `any` допускается только на документированной границе совместимости;
- внешний ввод проходит от `unknown` к типу через валидатор;
- исчерпывающий `switch` обязателен для закрытых объединений;
- сравнение использует строгую семантику;
- исключение содержит распознаваемый тип либо преобразуется в проектную
  ошибку;
- вложенный тернарный оператор запрещён;
- отключение правила требует причины и ссылки на задачу либо положение;
- подавление охватывает минимально возможную строку или блок.

Автоматическое исправление ESLint разрешено локально для правил, которые
сохраняют смысл. CI запускает режим проверки и не изменяет файлы.

### BASE-L03. Публичный экспорт

Публичный модуль использует именованные экспорты и объявляет минимальную
доступную поверхность. Экспорт по умолчанию допускается в конфигурационных
файлах, где его требует инструмент. Внутренний элемент не экспортируется
только ради удобства теста; проверка обращается к публичной границе либо к
выделенному чистому модулю с самостоятельным контрактом.

### BASE-L04. CSS-профиль

При наличии CSS Stylelint проверяет синтаксическую корректность, неизвестные и
дублированные свойства, конфликтующие декларации и другие применимые правила
поддерживаемого стандартного профиля. Предупреждения в CI запрещены.

Prettier управляет синтаксической формой CSS. Порядок групп свойств,
контейнерные соглашения и способ изоляции компонентов закрепляются локальным
правилом, когда проекту требуется единая политика сверх BASE-CSS-N01.

## 7. Смысловые имена

### BASE-N01. Смысловое имя

Смысловое имя по G032 применяется к каталогу, файлу, модулю, типу, классу,
функции, переменной, команде и CSS-селектору и сообщает предмет либо
ответственность элемента. Оно позволяет
новому участнику определить назначение и вероятное место изменения без
предварительного чтения всей реализации.

Одно понятие получает один основной термин во всём проекте. Термины
согласуются со Словарём. Сокращение применяется после определения либо при
однозначности внутри профессионального контекста.

Слова `data`, `item`, `object`, `manager`, `service`, `handler`, `processor`,
`helper`, `utils`, `common`, `misc` и `core` требуют названного предмета и
конкретной ответственности. Обозначения `new`, `old`, `final`, порядковый
номер и случайная визуальная характеристика не заменяют смысл. Имена
`processData`, `FileManager`, `utils/`, `new-module.ts` и `wrapper2`
семантически недостаточны.

### BASE-N02. Грамматика и единство имён

Функция и команда называют действие и предмет, например
`buildIntegrityManifest` и `compareCanonicalCorpus`. Тип и класс называют
сущность, состояние либо ответственность, например `CanonicalCorpus` и
`ReleaseEvidence`. Булево значение формулируется как утверждение и начинается
с `is`, `has`, `can`, `should` либо другого глагола состояния. Тест называет
подтверждаемое или отклоняемое поведение.

Проектные файлы и каталоги используют `kebab-case`; переменные и функции
TypeScript и JavaScript — `camelCase`; типы и классы — `PascalCase`;
константы конфигурации верхнего уровня — `UPPER_SNAKE_CASE`. Имена, прямо
назначенные Учредительным профилем, контрактом инструмента либо устойчивым
корневым соглашением, сохраняют объявленную форму: `README.md`, `LICENSE.md`,
`LOCALE.json` и `CONSTITUTION_CODE.md`. Однотипные элементы сохраняют общую
морфологию и порядок смысловых частей.

### BASE-N03. Смысловая иерархия

Условные корни `src`, `test`, `docs`, `dist` и `.github` сообщают техническую
роль. Первый проектный уровень внутри них называет предметную область,
возможность либо конкретную границу. Архитектурные слова `domain`,
`application`, `adapters`, `infrastructure` и `services` располагаются внутри
уже названного смыслового контекста.

Требование действует для любого языка и снижает стоимость входа в работу.
Ограниченность Bash лишь делает ценность точного имени особенно заметной. В
IRONCREED имена
`ironcreed::integrity_build_manifest`, `baseline-promote.sh`,
`topology-discovery.sh` и `ioc-scan.sh` раскрывают пространство, действие и
предмет; TypeScript получает от той же точности такую же пользу.

### BASE-CSS-N01. Имена CSS

CSS использует `kebab-case` и называет компонент, роль либо состояние. Внутри
одной области применяется один согласованный способ образования имён
дочерних элементов и модификаторов. BEM, CSS Modules и локальная компонентная
схема допустимы; ни одна из них не является обязательной для всех проектов.

Имена `.constitution-index`, `.constitution-index-title` и
`.constitution-index.is-expanded` образуют читаемую локальную систему. Имена
`.box2`, `.left`, `.red-text` и `.wrapper-final` описывают случайную форму
либо историю правки и отклоняются. Автоматика проверяет форму и локальную
согласованность, а достаточность смысла подтверждается ревью.

## 8. Структура программ

### BASE-A01. Направление зависимостей

Внутреннее ядро содержит модели, правила и детерминированные преобразования.
Адаптеры связывают ядро с файловой системой, Git, консолью, часами,
хешированием и форматами хранения. CLI разбирает команду, вызывает прикладной
сценарий и преобразует результат в код завершения.

Предлагаемая структура:

```text
src/
  constitution-corpus/
    domain/
    application/
    adapters/
  release-evidence/
    application/
    adapters/
  constitution-cli/
    composition-root.ts
    main.ts
test/
  constitution-corpus/
  release-evidence/
  fixtures/
```

`domain` не импортирует `application`, `adapters` или CLI. `application`
зависит от доменных контрактов. `adapters` реализуют внешние контракты.
Конкретный `composition-root.ts` образует точку композиции по G033 и связывает
реализации для исполняемой точки;
весь каталог CLI не получает неограниченного права импортировать любые
внутренности. CLI не содержит правил корпуса.

### BASE-A02. Контракты и границы модулей

Каждый модуль объявляет публичную границу, направленные зависимости и
владельца изменяемого состояния. Циклы между модулями запрещены. Технические
типы файловой системы, Git, консоли, часов, хеширования, Markdown-парсера и
валидатора схем не проникают во внутреннюю модель.

Прикладной сценарий зависит от порта, а адаптер подтверждает соответствие
этому порту контрактным тестом. Точка композиции знает конкретные реализации,
но не принимает предметных решений.

### KCR-A01. Конвейер документа

Конвейер различает операции:

1. чтение исходных байтов;
2. синтаксический разбор;
3. построение индекса положений и диапазонов;
4. валидацию структуры;
5. классификацию и план дробления;
6. извлечение точных срезов источника;
7. построение манифеста;
8. обратную сборку;
9. сравнение, хеширование и отчёт.

Парсер распознаёт структуру. Валидатор сообщает нарушения. Трансформер создаёт
новое представление. Сериализатор записывает представление. Эти обязанности
сохраняются раздельно и используют термины из `kcr-glossary-001`.

### KCR-A02. Сохранение исходного текста

AST определяет границы структурных блоков, а дробление извлекает исходные
срезы байтов. Полная повторная сериализация Markdown-парсером не используется
для неизменённого круглого прохода. Это сохраняет пробелы, таблицы, HTML-якоря,
переносы и авторскую форму текста.

Сборка неизменённых частей должна возвращать исходную последовательность
байтов. Сборка изменённых частей создаёт новый кандидат источника и никогда
не объявляет тождество с прежним хешем.

## 9. Тестирование и доказательства

### BASE-Q01. Виды тестов

Проверочный контур различает следующие виды тестов:

| Вид | Предмет |
| --- | --- |
| Модульный | Чистые правила, преобразования и граничные значения |
| Контрактный | Соответствие каждого адаптера порту прикладного уровня |
| Интеграционный | Файловая система, временный Git-репозиторий, CLI, коды завершения и полный сценарий |
| Архитектурный | Направления импортов, отсутствие циклов и проникновения технических типов внутрь |
| Негативный | Предсказуемый отказ, отсутствие частичного результата и сохранение канонического источника |

Тест обращается к публичной границе модуля. Внутренний порядок вызовов
фиксируется только там, где последовательность является частью наблюдаемого
контракта.

Фикстура получает устойчивый ID, назначение, происхождение, применимые
правила, ожидаемый результат и статус положительного либо отрицательного
примера. Массовое обновление ожидаемых результатов не считается
доказательством корректности: каждое содержательное различие рассматривается
отдельно. Случайная генерация использует воспроизводимый seed и сообщает его
при отказе.

### KCR-Q01. Инварианты корпуса

Обязательные инварианты:

- каждый нормативный смысловой блок имеет один устойчивый ID;
- каждый ID уникален в своём пространстве;
- каждая ссылка разрешается в объявленной редакции;
- история происхождения не содержит циклов;
- выведенный ID не используется повторно;
- каждое положение классифицировано по одному каноническому месту;
- каждая производная часть содержит только заявленные ID;
- неизменённый проход `assemble(split(source))` тождествен исходным байтам;
- изменение части обнаруживается хешем;
- таблицы сохраняют число ячеек и заголовки;
- карта вопросов разрешается к существующим положениям;
- сборка детерминирована в разных рабочих каталогах.

### BASE-Q02. Карта правила к проверке

Каждый нормативный инвариант связывается хотя бы с одной автоматической
проверкой либо явно назначенным человеческим ревью. Реестр соответствия
содержит ID правила, область, средство проверки, положительные и отрицательные
фикстуры и требуемое доказательство. Процент покрытия сохраняет
диагностическую роль; обязательность задаёт карта `правило → проверка`.

Изменение правила обновляет карту и применимые проверки в том же проходе.
Правило без исполнимой автоматической формы получает конкретный предмет
человеческого ревью, а не безадресную пометку `manual`.

### BASE-Q03. Полная проверка

`npm run check` является единой немутирующей и детерминированной командой. Она
работает без сети, записывает временные результаты за пределами канонических
источников и завершается успешно только после исполнения всех применимых
проверок. Независимые стадии способны выполняться параллельно, сохраняя
одинаковый итог и диагностику.

Полный проход включает:

1. формат TypeScript, JavaScript, CSS и конфигурационных файлов;
2. Markdown-линтинг;
3. ESLint для TypeScript и JavaScript;
4. TypeScript typecheck;
5. Stylelint при наличии CSS;
6. модульные, контрактные, интеграционные, архитектурные и негативные тесты;
7. схемы, реестры и манифесты;
8. локальные инварианты KCR;
9. лицензионные декларации и точный SHA `.licensing-policy/`;
10. чистоту производных результатов и отсутствие изменений, созданных самой
    проверкой.

Отказ ранней проверки завершает проход ненулевым кодом. Отчёт называет
правило, файл, место, конституционное либо законодательное основание и
предлагаемое безопасное действие.

### BASE-Q04. Удостоверение проверки

Проверочный порядок различает три объекта:

- тест или проверка — воспроизводимое правило;
- результат прохода — свидетельство применения правила к точному состоянию;
- выпускной отчёт — долговременно сохраняемое доказательство принятого
  кандидата.

Итоговый отчёт успешного прохода содержит Git SHA, хеш lockfile, версии
Node.js и npm, манифест инструментов, применимую редакцию настоящего акта,
результаты стадий, активные исключения и хеши проверенных производных
результатов. Время, операционная система и среда выполнения хранятся в отчёте
как сведения наблюдения и не включаются в детерминированные артефакты.
Изменение кандидата прекращает действие результата проверки.

Диагностика сообщает ID нарушенного правила, файл, место и безопасное
действие, когда оно известно. Связь правила с Конституцией определяется
реестром актов; отдельное сообщение линтера не воспроизводит полный
теоретический комментарий.

## 10. Зависимости и обновления

### BASE-D01. Принятие зависимости

Для каждой прямой зависимости фиксируются её функция, область использования,
статус `runtime` либо `development`, источник, лицензия, поддерживаемая линия,
причина выбора и существенные риски. Зависимость с исполняемым установочным
скриптом, нативным кодом либо доступом к внешнему ресурсу получает отдельную
оценку.

Зависимость принимается при наличии определённой функции, совместимого
лицензионного порядка, поддерживаемой линии выпуска и доказанного преимущества
перед небольшой локальной реализацией. Прямые зависимости перечисляются
явно.

Обновление зависимости проходит тесты и просмотр изменений поведения.
Обновление Markdown-парсера, сериализатора, валидатора схемы, форматтера,
линтера, TypeScript, Node.js либо набора правил получает отдельную запись
решения независимо от класса версии, поскольку способно изменить нормативные
доказательства и представления. Нормативным является набор правил,
разрешённый точной версией lockfile.

### BASE-D02. Воспроизводимость

`package.json` объявляет поддерживаемые диапазоны, а `package-lock.json`
устанавливает точное разрешённое дерево и контроль целостности. Изменение
lockfile содержит только последствия заявленного обновления. CI устанавливает
зависимости без плавающего разрешения версий.

Манифест инструментов записывает Node.js, npm и версии средств, влияющих на
байты или результат проверки. Выпуск включает производный перечень прямых и
транзитивных зависимостей с точными версиями, лицензиями и
integrity-значениями. Сеть не используется внутри дробления, сборки и
локальной валидации.

### BASE-D03. Аудит зависимостей

Проверка актуальных сведений об уязвимостях выполняется отдельным сценарием
`npm run audit:dependencies`, поскольку внешняя база рекомендаций изменяется
во времени. Сценарий запускается при изменении дерева зависимостей, по
расписанию и перед выпуском. Отчёт указывает источник и момент получения
данных.

Решение учитывает достижимость уязвимого пути, роль зависимости и последствия
для проекта. Внутреннее исключение не создаёт отсутствующего лицензионного
разрешения и не отменяет обязательный внешний порядок.

## 11. Исключения и локальные правила

### BASE-X01. Временное исключение

Исключение по G035 временно разрешает ограниченное отступление и содержит:

- собственный устойчивый ID;
- точный адрес правила;
- минимальную область файлов или операций;
- основание и оценку риска;
- компенсирующую проверку;
- владельца и утвердившего субъекта;
- начало, срок окончания и условие досрочного прекращения;
- доказательства;
- состояние: `proposed`, `active`, `expired`, `revoked` или `replaced`.

CI допускает подавление только при ссылке на действующую запись, показывает
результат как `waived`, а не как обычный `passed`, и отклоняет просроченное
исключение. Продление создаёт запись-преемник. Бессрочное решение изменяет
соответствующую норму обычным порядком. Конфигурационный комментарий без
записи основания не создаёт исключения.

Исключение не затрагивает защищённые положения, целостность канонического
источника, человеческую атрибуцию полномочия и требования обязательного
внешнего порядка.

### BASE-X02. Локальное правило

Новое локальное правило по G034 возникает из повторяемого дефекта, принятого
архитектурного решения, ограничения технологии либо требования внешнего
порядка. Запись правила содержит:

- устойчивый ID;
- источник намерения;
- область;
- требуемое поведение;
- автоматический либо человеческий способ проверки;
- примеры соответствия и нарушения;
- порядок изменения;
- отношение к переносимому ядру.

Локальное правило заранее конкретизирует переносимое ядро для проекта.
Исключение обслуживает временное отклонение. Аварийная мера действует по P14.
Такой порядок позволяет переносить `BASE` между проектами и сохранять правила
контейнера CSS, границ модуля или формата конкретного манифеста в явном
расширении.
